# KUB-A VLAN 82

**Created:** 2026-10-30  
**Last updated:** 2026-10-30

**Implementation date:** 2026-10-30  
**Status:** Complete  
**Affected systems:** new network KUB-A (VLAN 82), new zone `AlphaSec-Kube`, port profile `Proxmox-Trunk`, eight new firewall policies, the `win11-dev` client entry

On 2026-10-30 I created KUB-A, an isolated network for my self-hosted GitHub Actions runners. Runner jobs execute code from public repositories, so the network reaches the internet, my monitoring and Wazuh, and admits admin access from four named hosts. It reaches nothing else. The platform record is [Phase 1 Build](../../../../../Platforms/CI%20Runners/Documentation/Change%20Records/Phase%201%20Build%20-%202026-10-30.md).

## What changed

1. **Zone.** `unifi_list_firewall_zones` returned 12 zones and no `AlphaSec-Kube`. I created `AlphaSec-Kube`, ID `6ae4cd7de2482aecb956b811`.
2. **Network.** `unifi_list_networks` returned no VLAN 82 and no `192.168.82.0/24`. I created KUB-A, ID `6ae4cd88e2482aecb956b81c`: corporate, VLAN 82, `192.168.82.1/24`, DHCP `192.168.82.100` to `.150` with a 86,400-second lease, IPv6 off, IGMP snooping, UPnP and network isolation off, in zone `AlphaSec-Kube`. The readback reported 17 persisted fields with none dropped or coerced. Two earlier attempts were rejected before creation, first for the read-only `mdns_enabled` and then for the unknown fields `networkgroup` and `setting_preference`, and created nothing.
3. **Trunk.** The controller added KUB-A to `Proxmox-Trunk`'s exclusion list on creation. I removed it and changed nothing else; the readback showed `excluded_networkconf_ids` back to Management, IoT, Trusted, Secure and Proton-WiFi. `Server-Provision` still excludes KUB-A.
4. **Policies.** I created eight policies, all enabled, both IP versions, schedule `Always`:

The four admin sources are `ubuntu-dev`, `docker-blue` (SSH Manager), `ansible-01` and Jedi PC. Port 9182 is there for a Windows exporter on `win11-dev`, which is not installed yet.

5. **`win11-dev` reservation.** After `win11-dev` moved to KUB-A at static `192.168.82.11`, I set its client entry's `use_fixedip` to false. The readback showed `use_fixedip: false` and an empty `fixed_ip`.

## Verification

A full policy list returned 415 policies, and the ones naming `AlphaSec-Kube` showed the generated defaults: `Block All Traffic` between KUB-A and every Internal and custom zone in both directions, `Allow All Traffic` to Gateway and External, and `Block All Traffic` within the zone. My eight policies and their four response companions sat on top. The Kube-to-External ordering returned three before-system entries, and the indexes put the block last.

Traffic from `ci-k3s-01` confirmed it. HTTPS to `github.com`, HTTP to `deb.debian.org`, DNS to `192.168.82.1` and Wazuh on `192.168.72.2:1514` connected. DNS and SSH to `1.1.1.1`, Splunk on `192.168.72.3:514`, `ansible-01:22`, `alpha-prod-01:22`, Grey's `8006` and HQ-DC01's `389` timed out. From `ubuntu-dev`, SSH to both runner hosts connected, and SSH Manager on `docker-blue` reached both.

The generated `Block All Traffic` within the zone does not separate `ci-k3s-01` and `win11-dev`. They share the subnet, so their traffic never reaches the gateway, and `ci-k3s-01` connected to `win11-dev` on port 22.

## Rollback

Delete the eight policies, set KUB-A back on the `Proxmox-Trunk` exclusion list, delete KUB-A, then delete `AlphaSec-Kube`. Move `win11-dev` back to VLAN 40 first, and restore its `192.168.40.117` reservation.
