# Collector DNS Failure After a Boot Race

**Created:** 2026-08-27  
**Last updated:** 2026-08-27

**Date:** 2026-08-27  
**Scope:** The TeamSpeak dashboard reported both public addresses down for 17 days while both voice servers were up and serving clients. Fix the cause, not the symptom, and stop the dashboard reporting the monitoring's own blindness as an outage.

## Symptom

The Grafana TeamSpeak dashboard showed `DOWN` for `Public address reachable` on `ts02` and `ts03`. Clients were connected to both servers at the time.

## What the metrics actually said

```
teamspeak_local_up{server="ts02"}    1      voice answering on 127.0.0.1:9988
teamspeak_local_up{server="ts03"}    1      voice answering on 127.0.0.1:9989
teamspeak_query_up{server="ts02"}    1      ServerQuery logging in
teamspeak_clients_online{...}        1      a client actually connected
teamspeak_dns_srv_up{server="ts02"}  0      <-- the SRV lookup failed
teamspeak_public_up{server="ts02",relay="unresolved:0"}  0
teamspeak_tunnel_fault{server="ts02"} 1
```

The `relay` label read `unresolved:0`. That label is written from the SRV lookup on every cycle, so it was already saying the collector never learned an address to probe. `teamspeak_public_up` was 0 because the probe never ran, not because the probe ran and failed.

## Isolating it

The records themselves were fine. From my workstation and from `alpha-prod-01` itself:

```
$ dig +short SRV _ts3._udp.ts02.alphasecunited.com
0 0 53810 needs-charter.gl.at.ply.gg.
$ dig +short SRV _ts3._udp.ts03.alphasecunited.com
0 0 49125 gets-wrestling.gl.at.ply.gg.
```

Inside the container:

```
$ docker exec teamspeak-monitor dig +short SRV _ts3._udp.ts02.alphasecunited.com
;; communications error to ::1#53: connection refused
;; communications error to 127.0.0.1#53: connection refused
;; no servers could be reached                      (rc=9)
```

`dig` was present, since the image installs `bind-tools`, and falling back to localhost is what `dig` does when `/etc/resolv.conf` names no server. The container's file:

```
# Generated by Docker Engine.
# This file can be edited; Docker Engine will not make further changes once it
# has been modified.


# Based on host file: '/etc/resolv.conf'
# Overrides: []
```

Zero `nameserver` lines. The host's own file was correct: `nameserver 192.168.80.1`.

## Cause

A boot race, frozen in place by Docker's copy-once behaviour.

```
container StartedAt      2026-08-10T18:22:49Z  = 14:22:49 -0400
/etc/resolv.conf mtime   2026-08-10 14:22:51 -0400
```

The host booted on 2026-08-10. Docker created the container at 14:22:49, while `dhcpcd` had not yet written the `nameserver` line. It landed two seconds later at 14:22:51. Docker copies the host's `/etc/resolv.conf` into the container once, at creation, and as its own generated header says, never revisits it. `RestartCount` was 0 and the container had been up 2 weeks, so nothing ever re-read the corrected file.

Every DNS lookup in that container had failed for 17 days. `socket.gethostbyname` failed the same way (`[Errno -3] Try again`), so even a hardcoded relay hostname would not have helped.

The date is not a coincidence: 2026-08-10 is the same fleet restart that left Prometheus stopped, recorded as [Prometheus issue 5](../../../Prometheus/Documentation/Troubleshooting/Container%20Remained%20Stopped%20After%20monitor-01%20Restart%20-%202026-08-10.md).

## Correction

Pin the resolver in the Compose file rather than inheriting whatever the host file held at creation:

```yaml
    network_mode: host
    dns:
      - 192.168.80.1
```

`dns:` is honoured under `network_mode: host` on Docker 29.6.2. I checked that before relying on it rather than assuming it, because the option is documented as ignored in some older versions:

```
$ docker run --rm --network host --dns 192.168.80.1 alpine:3 cat /etc/resolv.conf
...
nameserver 192.168.80.1

# Based on host file: '/etc/resolv.conf'
# Overrides: [nameservers]
```

`Overrides: [nameservers]` is the confirmation. Without `--dns` the same command produced `Overrides: []` and copied the host file, which now carries the nameserver, which is precisely why a plain restart would also have fixed this, and why it would break again on the next slow boot.

A bind mount of `/etc/resolv.conf` would also track the host, and I rejected it. It is a single-file mount, and `dhcpcd` replaces that file rather than writing through it, so the container would pin the old inode, the same failure already recorded twice in this repository for `prometheus.yml`.

## Verification

```
$ docker compose config                        # valid
$ docker compose up -d                         # Recreated, Started
$ docker exec teamspeak-monitor cat /etc/resolv.conf
nameserver 192.168.80.1
# Overrides: [nameservers]
$ docker exec teamspeak-monitor dig +short SRV _ts3._udp.ts02.alphasecunited.com _ts3._udp.ts03.alphasecunited.com
0 0 53810 needs-charter.gl.at.ply.gg.
0 0 49125 gets-wrestling.gl.at.ply.gg.
```

The textfile 20 seconds later:

```
teamspeak_dns_srv_up{server="ts02"} 1
teamspeak_public_up{server="ts02",relay="needs-charter.gl.at.ply.gg:53810"} 1
teamspeak_public_rtt_seconds{...} 0.039814
teamspeak_tunnel_fault{server="ts02"} 0
teamspeak_server_fault{server="ts02"} 0
```

Same shape for `ts03` at `gets-wrestling.gl.at.ply.gg:49125`, 0.041051 s. Confirmed through Prometheus after the next node_exporter scrape: all ten reachability series green.

The 40 ms round trip matches the 44–46 ms measured when the collector was built, so the public path was never actually broken.

## What the dashboard now does about it

The metrics were right and the dashboard framing was wrong. `teamspeak_dns_srv_up` had been 0 the whole time and no panel led with it, so a monitoring fault presented as a service outage.

The rebuilt dashboard puts **Name resolution** in the top row beside **Public address** and **Local voice**, adds a **Relay endpoints** table that renders `unresolved:0` as `unresolved — DNS failed` in red, and says in the `Verdict` panel's own description that `PUBLIC PATH DOWN` has three possible causes and name resolution is the one to check first. Detail in the Prometheus change record [Dashboard Rebuild and Per-Node Boards - 2026-08-27](../../../Prometheus/Documentation/Change%20Records/Dashboard%20Rebuild%20and%20Per-Node%20Boards%20-%202026-08-27.md).

## Fleet sweep

Every container on every host that resolves names and was created during a boot carries this risk.
`teamspeak-monitor` is the one that announced it, by having a metric whose only job is to report DNS.
So I swept the fleet on 2026-08-27:

```bash
for c in $(docker ps -q); do
  n=$(docker exec "$c" sh -c 'grep -c "^nameserver" /etc/resolv.conf' 2>/dev/null)
  [ "$n" = "0" ] && echo "BROKEN $(docker inspect -f '{{.Name}}' "$c")"
done
```

| `media-01` | 10 | clean |
| `alpha-prod-01` | 7 | clean, after the fix above |

52 of 60 running containers verified, none affected. The eight unchecked containers on `security-01` and
`game-01` are the open part of this: run the loop there with a root shell to close it. Neither host reported
a symptom, but neither runs a container whose job is to notice.

## Rollback

`docker-compose.yml.bak-2026-08-27` sits beside the deployed file on `alpha-prod-01`. Restore it and
`docker compose up -d` to return to the inherited-resolver behaviour. There is no reason to.
